# ADR 0004：符号索引与确定性冲突解决

- 状态：Accepted
- 日期：2026-10-04

## 背景

Phase 1 的同步报告是文件级的：“这 8 个文件需要复核”。NautilusTrader v1.230.0 → v1.231.0 的试点暴露了两个问题：

1. **没有冲突、但已经过时的注释**无法定位。例如 `resolve_no_side_order` 的实现新增了 `AmbiguousOrderSide` 分支，
   合并没有冲突，注释却已经不完整——只能靠人逐个函数比对。
2. **合并冲突**需要手工处理，而冲突几乎总是“中文注释紧挨着上游改动”。

## 决策

### 符号索引

- Rust、Python 使用 tree-sitter；Cython（`.pyx` / `.pxd`）tree-sitter-python 无法解析 `cdef`，使用基于缩进的提取器。
  其余文件类型降级为文件级跟踪。
- 符号 ID：`<path>#<qualname>`，如 `book.rs#impl OrderBook::apply_delta`、`engine.pyx#RiskEngine.check`；
  同名（`#[cfg]` 变体）追加 `~2`。`#[cfg(test)]` 与 `mod tests` 不索引。
- 三类哈希，计算前**剔除 【zh】 行并归一化空白**，因此学习版与上游原文哈希相同，纯格式化改动不触发 stale：
  - `sig`：属性 / 装饰器 + 声明头（API）
  - `doc`：前导注释、文档注释、docstring（英文原文）
  - `body`：实现；容器（impl / trait / mod / class）的 body 用占位符替换子符号，方法内部的改动不会让整个类变 stale
- 注释归属：一段连续的 【zh】 行归属于**包含它的最内层符号**（符号范围包含其前导文档与属性）；都不包含则归 `<module>`。
- 计入覆盖率的符号：类型定义、有英文文档的条目、实现体 ≥ 5 行的函数，以及每个文件的 `<module>`；impl 块被索引但不计入。

### 确定性冲突解决

由剥离不变式，学习分支上任一上游文件 = `upstream_old + 【zh】`。因此合并后的**代码必然等于 upstream_new**，
只需要放置注释：

1. 对“我方”（学习分支）每段注释，记录所属符号、紧随其后的代码行、紧邻其前的代码行；
2. 在 upstream_new 中找到同一符号，在其范围内寻找相同的“后一行”（多个候选时优先前一行也匹配、且相对位置最接近的）；
3. 后一行已被改写时，改用“前一行”定位，插在其后；
4. 都找不到时挂到符号开头并在报告中标记“需确认位置”；符号已删除则作为孤儿写入报告（附原文），不插入。

## 试点验证（NautilusTrader v1.230.0 → v1.231.0，592 个上游提交）

| | Phase 1（文件级） | Phase 2（符号级） |
|---|---|---|
| 报告的复核项 | 8 个文件 | 12 个符号（按 P0/P1/P2 排序） |
| 人工复核找到的过时注释 | 4 处 | 4 处全部命中，并多发现 6 处人工漏掉的 |
| 冲突 | 2 个文件需手工解决 | 自动解决，28 段注释重新挂载，位置与人工结果完全一致 |

## 后果

- 同步后的工作变成一个有优先级的队列：`osca queue` → 修改注释或 `osca review approve`。
- 依赖 tree-sitter（锁定 `<0.26`：0.26.0 在本项目的使用方式下会段错误）。
- 宏生成的条目、`include!` 等无法被索引，相关注释归入 `<module>`。
